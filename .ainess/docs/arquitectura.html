Auditoría de deuda técnica

Lógica rota en removeMessage

Severidad Alta

La condición de borrado es msg.platform !== platform && msg.hash !== hash. Si se manda a borrar un mensaje de Kick con hash 123, otro mensaje distinto de Twitch con hash 456 se evalúa como 'twitch' !== 'kick' && 456 !== 123 que es true && true = true (se conserva). PERO cualquier mensaje de Kick, sin importar el hash, se evalúa con false && ... = false y se elimina por completo. Borrar un solo mensaje limpia todo el chat de esa plataforma.

// src/contexts/messagesContext.tsx const removeMessage = (platform: MessagePlatform, hash: number) => { setMessages((prev) => prev.filter(msg => msg.platform !== platform && msg.hash !== hash)); };

Corrección: Usar la negación de la condición exacta: !(msg.platform === platform && msg.hash === hash).

Fuga de memoria por array sin límite

Severidad Alta

El estado messages pushea todo mensaje nuevo sin recortar los viejos. En streams largos, acumula miles de nodos en memoria y fuerza a React a hacer diffs inmensos degradando el render.

// src/contexts/messagesContext.tsx setMessages((prev) => { if (!prev.some(msg => msg.hash === message.hash && msg.platform === message.platform)) { return [...prev, message]; } return prev; });

Corrección: Implementar un cap (ej: mantener últimos 100) y/o TTL temporal (borrar de la cola visual tras 30-60 segs).

Estados de carga visibles en OBS

Severidad Media

Los providers de Kick y Twitch renderizan un div de carga si aún no inicializaron. Al usar reduceRight, los providers envuelven a ChatViewClient en el DOM. Esos divs bloquean y se renderizan sobre la pantalla limpia que captura OBS.

// src/contexts/tmiContext.tsx if (loading) { return <div>Loading twitch client...</div>; }

Corrección: Proveer el estado de conexión a través del contexto en lugar de bloquear el árbol de renderizado del componente envolvente.

Falta de cleanup en EventEmitter

Severidad Media

La clase propia de eventos carece de función off. Esto genera un leak de listeners si un componente se monta múltiples veces (ej. StrictMode de React), multiplicando la ejecución de handlers.

// src/lib/eventEmitter.ts export class EventEmitter { // No hay método 'off' o 'removeListener' on(event: string, listener: (...args: any[]) => void) { ... } }

Corrección: Agregar un método off(event, listener) o que on devuelva una función desuscriptora.

Uso bloqueante de window.location

Severidad Baja

Se lee el querystring usando el objeto global de ventana en el useEffect (con dependencias vacías), ignorando useSearchParams. Rompe con paradigmas de ruteo de Next.

// src/contexts/kickContext.tsx const channel = new URLSearchParams(window.location.search).get('kick');

Corrección: Usar const searchParams = useSearchParams() y añadirlo a las dependencias, o pasar los canales requeridos directamente por props.

Parseos desperdiciados en Kick

Severidad Baja

parser.ts procesa eventos de subscripciones, hosts y encuestas de Kick, pero el consumidor en kickContext.tsx descarta todo lo que no sea ChatMessage.

// src/lib/kickChat/parser.ts case "App\\Events\\SubscriptionEvent": { ... } case "App\\Events\\GiftedSubscriptionsEvent": { ... }

Corrección: Aunque no es perjudicial ahora, estos eventos deben conectarse con el sistema futuro de alertas.

Typos y 'any' con eslint-disable

Severidad Baja

Archivo mal nombrado colots.ts. Abuso ocasional de puentear Typescript.

// src/app/chat/page.tsx // eslint-disable-next-line @typescript-eslint/no-explicit-any const providers : React.FC<any>[] = [];

Corrección: Renombrar a colors.ts. Tipar providers como un React Context Provider genérico.

Arquitectura objetivo

El núcleo pasará de un estado acoplado a React Context a un Bus de Eventos central (EventBus) agnóstico de UI. Los clientes (Kick, Tmi, YT) actúan como Adapters que emiten StreamEvent, y un Registry de overlays (montado en /overlay/[type]) consume lo que necesita.

export type StreamEvent = | { type: 'chat.message'; payload: ChatMessage } | { type: 'chat.delete'; payload: { messageId: string } } | { type: 'sub' | 'sub.gift' | 'follow' | 'raid' | 'cheer'; payload: AlertPayload } | { type: 'music.nowplaying' | 'music.changed'; payload: TrackInfo }; export interface OverlayDefinition { id: string; name: string; component: React.ComponentType<any>; events: StreamEvent['type'][]; defaultConfig?: Record<string, unknown>; }

Roadmap por fases

Fase 0: Arreglo de deuda y estabilidad

Esfuerzo: Bajo

Arreglar bugs críticos que impiden streams largos sin problemas.

Solucionar el borrado agresivo de `removeMessage`. Implementar un límite flexible de ~100 mensajes usando slice en el setter de React. Renombrar typo `colots.ts`. Arreglar el `Loading` visible en OBS renderizándolo condicionalmente sin interrumpir `children`.

Fase 1: Bus de Eventos y Registry

Esfuerzo: Medio

Migración de la arquitectura estructural.

Crear EventBus reemplazando `EventEmitter` con tipado estricto `on/off/emit`. Definir type union `StreamEvent`. Desacoplar tmi/kick/yt para ser meros conectores al Bus. Reestructurar rutas hacia `/overlay/[type]` con alias legacy a `/chat`.

Fase 2: Overlay de Alertas

Esfuerzo: Medio-Alto

Consumo de los parsers de Kick abandonados y subscripciones de Twitch.

Crear el widget de alertas visuales. Requiere implementar una cola (Queue) ya que las animaciones visuales tardan y los eventos pueden dispararse en ráfaga (raids, gift bombs).

Fase 3: Contadores y Estadísticas

Esfuerzo: Bajo

Widgets complementarios de menor interacción.

Overlays simples basados en métricas: contador de follows, metas de suscripción, medidores de hype. Consumen del EventBus sin encolamiento, solo actúan por pulsos (incrementando valores numéricos con animación simple de odómetro).

Fase 4: Integración de Música

Esfuerzo: Alto

Overlay Now Playing con fallback local y APIs de terceros.

Comenzar leyendo del scrobbler público de Last.fm y leyendo archivos locales `current_song.txt` que exportan los reproductores. Luego, añadir integración compleja PKCE para Spotify y Apple Music (requiere setup sever-side).

Fase 5: Studio de configuración

Esfuerzo: Alto

UI para generarle al usuario su URL de fuente de navegador.

Panel de control que permite elegir colores, fuentes, espaciados y genera dinámicamente un querystring (o base64 encoded config) para copiar y pegar en OBS.

Fase 6: Temas y Compartición

Esfuerzo: Medio

Exportar y compartir presets creados.

Estandarizar las configuraciones visuales en un JSON/Base64 para que un streamer pueda enviarle su "tema" a otro mediante una URL encriptada.

Decisiones abiertas

Configuración de Overlays

  • URL Querystring (Actual)

    Fácil de exportar y sin backend, pero URLs demasiado largas ensucian OBS.

  • Persistencia y Perfiles

    URLs limpias vinculadas a una DB/LocalStore, requiere cuentas o local-first storage persistente.

Layer Server-side

  • 100% Client-side (Actual)

    Menor costo de hosteo, corre en el browser. Bloquea APIs OAuth y Twitch EventSub (requieren webhook).

  • Backend Next.js Server

    Abre las puertas a auth real, pero eleva los costos operativos o fuerza un deploy Vercel/Node real.

Conexión a Kick

  • Cliente propio (Actual)

    Control total del websocket Pusher. Riesgo alto de romperse ante un mínimo cambio de API no documentado de Kick.

  • Usar librería de terceros

    Delegar mantenimiento en comunidad, perdiendo flexibilidad inmediata y dependiendo de updates externos.

Motor de Animaciones

  • framer-motion

    Ya instalado en React, muy potente y declarativo. Carga CPU al hacer interpolaciones en JavaScript.

  • CSS Puro / Tailwind transitons

    Descarga la animación al compositor del browser (GPU). Clave en overlays de OBS que corren en PCs bajo estrés de encoding.

Alcance del Proyecto

  • Solo Web

    Solo un sitio web y rutas web. Simple de mantener, complejo para leer archivos del disco (SMTC/música local).

  • Monorepo + Desktop App

    Wrapper Tauri o Electron para acceso a procesos locales, multiplicando el esfuerzo de mantenimiento.
