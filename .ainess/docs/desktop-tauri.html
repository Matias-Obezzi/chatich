De Web a Desktop: Arquitectura Tauri

La premisa, corregida

Arranquemos por ser honestos: una app Tauri ES un agente local. Es un proceso de sistema operativo corriendo en la máquina del streamer.

El argumento para justificar este salto no es "evitar el agente local" (que es exactamente lo que estamos construyendo), sino consolidar. En lugar de tener la configuración fragmentada entre la URL, una extensión de navegador inestable, un plugin de OBS oscuro o un companion app de terceros, ofrecemos una sola instalación first-party.

Tauri nos permite centralizar el control: autorización OAuth, lectura de música a nivel SO, y manejo de eventos. Todo empaquetado en una única pieza de software de la que somos dueños y responsables.

Modelo Híbrido de Tiers (Recomendación Central)

Mudar el proyecto a Tauri no significa matar la versión web en Vercel. Al contrario, la arquitectura correcta es un modelo de dos tiers donde compartimos casi todo el código de los overlays.

Feature Tier Web (Vercel) Tier Desktop (Tauri)
Onboarding Fricción cero (pegá la URL) Requiere instalación
Chat anónimo (Twitch, Kick, YT) Sí Sí
Overlays básicos por URL Sí Sí (localhost)
Música del Sistema (VLC, web) No Sí (GSMTC/MPRIS)
Alertas avanzadas (Sub, Bits) No (Twitch requiere OAuth) Sí (EventSub WS)
Recompensas de Canal No Sí

Esto no es una reescritura. Los componentes visuales de overlay en src/component/* se reúsan tal cual. Lo único que cambia es el transporte de eventos. El modelo StreamEvent y el EventBus (planteados en arquitectura.html) son la abstracción clave: al componente React de alertas no le importa si el evento de "Sub" viene de un hook tmi.js client-side, o si lo empuja un WebSocket local servido por Rust.

Arquitectura Tauri propuesta

Flujo de la aplicación de escritorio. Hacé clic en los nodos para inspeccionar su responsabilidad.

Proceso nativo
Core Rust
El cerebro de la operación. Maneja el estado, guarda secretos en el keychain, lee APIs de SO (música), hace polling a YT, sostiene la conexión a EventSub/Pusher y expone servidores locales.

¿Por qué los overlays siguen siendo web? Porque OBS Browser Source necesita una URL para renderizar. Intentar renderizar nativamente e inyectar el frame en OBS es una pesadilla de APIs y compatibilidad. Servir los overlays exportados desde Rust mediante un mini-servidor local (axum) en 127.0.0.1:PUERTO es confiable, ultra-rápido y permite reutilizar todo el código React.

Ruta de Migración (Fricciones Reales)

Tauri usa el frontend como archivos estáticos. Eso significa compilar Next.js con output: 'export'. Al analizar el código actual, esto rompe cuatro cosas específicas:

1. Middleware de cabeceras

src/middleware.ts : 16

middleware.ts no existe en export estático. Actualmente inyecta cabeceras como x-url, x-pathname y x-lang.

// src/middleware.ts response.headers.set("x-url", request.url); response.headers.set("x-lang", lang);

Solución: El frontend estático de Tauri debe usar cliente-side routing o hooks estándar. src/lib/context.ts dejará de depender de next/headers. La URL actual se lee con window.location o usePathname(), y el idioma se maneja por local-storage o config que inyecta Rust.

2. API Routes dinámicas

src/app/api/youtube/[id]/chat/route.ts

Los route handlers que corren en el servidor de Vercel desaparecen. Actualmente, el proxy a YouTube para evitar CORS está ahí.

// route.ts export const GET = async (request: Request, { params }) => { const url = `https://www.youtube.com/live_chat?v=${id}`; const content = await getYtInitialDataContent(url, request.headers);

Solución: Mudar la lógica de scraping y polling al backend de Rust usando reqwest. Rust no tiene restricciones de CORS. En vez de que React haga polling, Rust hace el polling y emite los mensajes parseados por el WebSocket local hacia el frontend.

3. Async Server Components

src/app/chat/page.tsx : 9

La página principal del chat es un Server Component asíncrono que lee el contexto (los headers dinámicos) antes de renderizar.

// src/app/chat/page.tsx export default async function Chat() { const context = await getContext(); const params = new URLSearchParams(context.search);

Solución: Convertir Chat a Client Component ("use client") y leer los parámetros de inicialización usando useSearchParams (envuelto en Suspense) o inyectándolos directamente al inicializar el Webview en Tauri.

4. Loaders de Webpack incompatibles

next.config.ts : 8

Se usa raw-loader para importar archivos Markdown de internacionalización directamente como strings en build-time.

// next.config.ts config.module.rules.push({ test: /\.md$/, use: 'raw-loader' });

Solución: Next.js soporta static export con loaders custom si son interpretables en build. Opcionalmente, se pueden migrar a JSON o cargar en runtime llamando a un Tauri Command (invoke('get_i18n', { lang })).

OAuth en Desktop: Por qué es MEJOR

Embeber Client Secrets en una app distribuida (binario, .exe, .dmg) es un error crítico de seguridad: cualquiera puede extraerlo. El RFC 8252 define cómo hacerlo bien: PKCE con cliente público.

Flujo de Autorización Nativo

  1. Rust genera un Code Verifier y Code Challenge aleatorio (PKCE).
  2. Rust abre el navegador del sistema operativo usando open o tauri-plugin-shell.
  3. El usuario se loguea en Twitch/Spotify en su browser habitual (aprovechando sesiones activas).
  4. Redirección. Dos opciones:
    • Deep link custom: chatich://oauth/callback (vía tauri-plugin-deep-link). Falla si el SO no registra bien el esquema.
    • Loopback HTTP (Recomendado): Rust levanta un miniserver temporal en http://127.0.0.1:PUERTO/callback. Confiable y no requiere permisos de admin.
  5. Rust recibe el code, y lo cambia por tokens usando el Code Verifier.
  6. Los tokens se guardan de forma segura en el llavero del SO usando tauri-plugin-stronghold o el crate keyring (Windows Credential Manager / macOS Keychain). ¡Nada de texto plano!
Plataforma Scopes clave Qué desbloquea
Twitch channel:read:redemptions, bits:read, channel:read:subscriptions Canjes de puntos de canal, alertas reales de bits, hype trains, subs. Todo por EventSub WebSocket.
Spotify user-read-currently-playing API para obtener track actual, carátula en HD e IDs de canciones, como fallback si las APIs del SO fallan.
YouTube yt-analytics.readonly (opcional) Acceso autenticado al LiveChat (más cuota y lectura de mensajes de miembros).

Detección de Música (OS Level)

La ventaja asesina de la app nativa: no depender de las APIs web de Spotify y resolver el agujero ciego que era YouTube Music en navegador. Rust puede preguntar al Sistema Operativo qué está sonando, sin OAuth.

Sistema Operativo Tecnología / API Estado y Alcance
Windows GSMTC (GlobalSystemMediaTransportControls) Excelente. Lee Spotify nativo, VLC, YouTube/YT Music en Chrome/Edge. Da título, artista y posición temporal. Accesible vía el crate windows.
Linux MPRIS (sobre D-Bus) Perfecto. Equivalente a Windows, soporte estándar en casi todos los reproductores.
macOS MediaRemote (API privada) Restringido. Apple limitó el acceso a NowPlaying a menos que pidas entitlements especiales. Probablemente se necesite depender de OAuth de Spotify o Apple Music web APIs como fallback.

Eventos con Permisos de Broadcaster

Con OAuth resuelto y un proceso demonio corriendo en Rust, el acceso a datos cambia drásticamente respecto al modelo 100% web.

Plataforma En la Web (Actual) En Tauri (Propuesto)
Twitch Solo IRC chat. Sin acceso a canjes, alertas de subs imprecisas. EventSub sobre WebSocket. Conexión oficial que escupe JSON con eventos perfectos de subs, raids, follows y canjes de puntos.
Kick Conexión WS no oficial a Pusher. Idéntico, pero el proceso Rust mantiene la conexión WS, aislando las caídas o cierres de ventana de OBS.
YouTube Proxy route en Vercel sujeto a rate limits. Polling directo desde Rust. Sin CORS, scraping directo de ytInitialData local o consumo agresivo de la API de Data V3 si hay OAuth.

Distribución y Operación

Distribuir binarios no es subir código a Vercel. Tiene fricciones reales de distribución que hay que afrontar:

  • Firma de Código (Code Signing): Obligatorio. En Windows, un ejecutable sin firmar levanta la alerta roja de SmartScreen ("Windows protegió su PC"), matando la conversión. Se necesita un certificado OV (USD ~200-400/año). En macOS, se requiere Notarización con cuenta de Apple Developer (USD 99/año).
  • Instalador: Tauri genera instaladores (MSI, NSIS, DMG, AppImage) por nosotros.
  • Actualizaciones: El plugin tauri-plugin-updater permite auto-updates. Rust descarga el delta y aplica el parche al reiniciar, manteniendo a los usuarios en la misma versión.
  • Comportamiento del SO: Al minimizar, va a la bandeja del sistema (System Tray). Iniciar con Windows (Autostart) requiere registro en el SO, fácil con Tauri.

Contras y Conclusión

Contras Honestos

  • Curva de Rust: El equipo tiene que meterse en un lenguaje de sistemas.
  • Mantenimiento Multi-OS: Las APIs de música (GSMTC vs MPRIS vs MediaRemote) obligan a escribir código específico por sistema operativo.
  • Fricción inicial: Se pierde el onboarding mágico de "pasame tu canal y te doy una URL". El usuario tiene que descargar e instalar.
  • Peso: Aunque Tauri es diminuto frente a Electron (~10MB vs ~120MB), sigue siendo un binario descargable.

Recomendación

Avanzar con el Modelo Híbrido, enfocando Tauri solo en Windows al inicio.

El 90% de los streamers usan Windows. Resolver la música con GSMTC y las alertas con EventSub en Windows valida el producto completo. Vercel queda encendido como herramienta de marketing y onboarding para usuarios casuales de solo-chat, compartiendo el 100% de los componentes React. Cuando el usuario quiere música que no sea Last.fm, o alertas con puntos de canal, el tier web le muestra el botón de descarga del tier Desktop.
