3. Comparativa técnica de integraciones

Análisis de las fuentes de datos disponibles para el estado Now Playing.

Fuente Datos OAuth / Auth Instalación Local Latencia Esfuerzo Notas
Spotify Todo (progreso, covers hi-res) OAuth 2.0 PKCE No Media (Polling) Medio API pública oficial. Endpoint /me/player/currently-playing. No tiene webhooks, requiere polling agresivo. Intercambio de tokens ideal en route handler de Next.
YouTube Music Casi todo No (oficial) Sí (extension/companion) Baja Alto No hay API oficial. Opciones: scraping o companion local (ej. th-ch/youtube-music) exponiendo HTTP en localhost. Trade-off: mucha fricción para el usuario.
Apple Music Todo Developer Token JWT + User Token No Baja Alto MusicKit JS. Developer token JWT firmado server-side (ES256) requiere Apple Developer Program (USD 99/año).
Last.fm Básico (sin progreso preciso) API Key (sin OAuth) Depende del scrobbler Alta Bajo user.getRecentTracks. Funciona como agregador universal si el usuario ya scrobblea. Falla en progreso en tiempo real y latencia.
Windows SMTC Básico (depende del reproductor) No Sí (App nativa) Baja (Tiempo real) Alto System Media Transport Controls. Solución universal que captura cualquier audio de Windows, pero nos obliga a mantener un `.exe` companion en C# o Rust.
OBS / Archivo local Texto plano (Título - Artista) No Sí (Snip, Tuna, etc.) Baja Bajo Leer `.txt` local. Cero fricción de desarrollo para nosotros, muy usado por streamers old-school, pero limitado en metadata (sin portadas fáciles).

4. Arquitectura propuesta

Se propone un patrón adaptador para normalizar cualquier fuente en una interfaz común MusicProvider.

type NowPlaying = { 
  source: 'spotify' | 'ytmusic' | 'apple' | 'lastfm' | 'smtc' | 'file'; 
  title: string; 
  artist: string; 
  album?: string; 
  artworkUrl?: string; 
  progressMs: number; 
  durationMs: number; 
  isPlaying: boolean; 
  updatedAt: number;
}

interface MusicProvider { 
  id: string; 
  connect(config: any): Promise<void>; 
  subscribe(callback: (np: NowPlaying | null) => void): () => void; 
  disconnect(): void; 
}

Flujo de Datos

Gestión de Estado y Tokens (El problema Stateless)

Chatich actualmente se configura 100% por querystring, sin base de datos. Para fuentes con OAuth (Spotify), guardar un refresh token en la URL presenta riesgos de seguridad y hace urls inmanejables por tamaño.

  • Opción A (URL cifrada): Cifrar el refresh token con un secreto del server y pasarlo en la URL (ej. ?spotify_token=abc123cifrado...). El server lo descifra al hacer peticiones. Mantiene la app stateless.
  • Opción B (Sesión Server-Side con Cookies): Crear un sistema mínimo de sesiones (ej. JWT en cookie HttpOnly). Rompe un poco el paradigma 100% url-based para compartir overlays, requiere que el streamer se loguee en el browser source de OBS (difícil) o use un código de vinculación.
  • Recomendación: Opción A. Crear una ruta intermedia /api/auth/spotify que haga el flujo OAuth, cifre el refresh token resultante con AES y redirija al usuario a una URL limpia con el token cifrado en el path o querystring. El overlay lee ese parámetro, hace ping al server y el server hace el polling a Spotify. Mantiene la portabilidad máxima de las URLs para OBS.
